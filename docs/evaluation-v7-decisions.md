# 评测第七阶段决策记录

状态：已决策，2026-10-30。承接[第六阶段决策](evaluation-v6-decisions.md)。

## 问题与选择

边界 fixture 已有典型反例数据，但目前只能手工改 SQL 来验证其区分力。本阶段增加版本化错误 SQL 清单和本地审计，让管理员看到每种错误在原始数据与边界数据上是否会被结果判分识别。

## 判定规则

1. 每个样例明确写出题目 ID、错误类型和可执行的错误 SQL。审计读取对应 oracle，在 `base`、`edge_v1` 上分别执行两条 SQL。
2. 错误 SQL 成功执行且结果与 oracle 不同时记为“识别”；结果相同记为“漏检”。执行失败记为“无效样例”，不得算作识别。
3. 总体“已识别”表示至少一个 fixture 识别；两个 fixture 都漏检才算“仍漏检”。每个 fixture 的计数分别展示，不把边界数据的改善归功于基础数据。
4. 审计仅使用固定本地 CSV 和 DuckDB，不调用 Agent 或远程模型，不保存评测运行记录。报告带任务、oracle、fixture 和错误 SQL 清单指纹，便于追溯。
5. 管理员 API 和现有 Vue 评测台提供手动触发入口。错误 SQL 是公开教学样例，用于审计测试集；它们不作为真实模型准确率或全部错误空间的覆盖率。

## 验收

- 至少覆盖漏状态过滤、错金额字段和错日期端点三类错误。
- 至少两个样例在 `base` 漏检、在 `edge_v1` 被识别，证明边界数据的增益。
- 无效 SQL 不计入识别；普通用户不能访问审计 API。
- 后端测试、前端类型检查及生产构建通过。
