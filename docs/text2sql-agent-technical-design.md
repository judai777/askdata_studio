# AskData Studio：受控 Text-to-SQL Agent 学习文档

> 本文是 AskData Studio V2 的学习文档，不是对某一套 Agent 框架的简单 API 说明。阅读目标是理解：为什么 Text-to-SQL 不能只靠一次 Prompt、如何把自然语言问数拆成可验证的阶段、如何用 Schema/RAG/Skill/MCP/权限/记忆把模型限制在可控边界内，以及如何用测试证明系统没有退化。

## 0. 版本与资料边界

本文以 **AskData Studio V2 当前代码**为事实基线，代码位于 `backend/app/`。配套面经包含 V1 项目实现、V2 演进后的实现，以及通用 Agent/RAG/Text-to-SQL 知识，三者必须分开理解。

### 0.1 V1 与 V2 的取舍

V1 的核心链路是：

```text
字段级 Schema 检索
  -> CoT/四元组规划
  -> Coder 生成 SQL
  -> 数据库执行
  -> Reflection 校验与回溯
```

V2 保留了 V1 中仍然有效的原则：Schema 约束、计划与执行分离、工具调用、执行反馈、权限和结果校验；但将实现收敛为更容易维护和测试的结构：

```text
请求预处理
  -> 字段级混合检索
  -> 最小连通 Schema 图
  -> Skill 约束的单库 Agent
  -> MCP 数据库工具
  -> SQL AST 与权限校验
  -> DuckDB 执行
  -> 结构化结果与结果说明
```

因此，以下 V1 内容只能作为历史背景或面试解释：

- 独立的 CoT 规划 Agent、Coder Agent、Reflection Agent 三 Agent 架构；
- CoT 四元组是当前系统固定中间协议；
- Chroma 是当前向量数据库；
- Qwen3-8B-Embedding 是当前 Embedding 模型；
- V1 的召回率、准确率、表数量和评测集规模数字。

V2 当前事实包括：请求预处理、`database_query/data_qa/direct_response` 三路由、字段级 Schema 索引、RRF/Rerank、Schema 图、LangGraph 澄清恢复、Skill 白名单、同进程 MCP、DuckDB CSV 执行、用户访问范围、结果表记忆和前端工作区。

### 0.2 如何使用这份文档

建议按以下顺序学习：

1. 先看第 1 节，建立完整请求链路；
2. 再看第 2～4 节，理解 Schema、检索、Agent 和 MCP 如何协作；
3. 阅读第 5～8 节，理解安全、记忆、结果输出和故障处理；
4. 最后看第 9～11 节，用测试、版本演进和面试问题检验理解。

每一节都回答三个问题：它解决什么问题、为什么这样设计、代码中在哪里实现。

## 1. 先建立全局模型

### 1.1 Text-to-SQL 到底要解决什么

Text-to-SQL 将业务人员的自然语言请求转换为数据库查询，并返回数据、SQL 和解释。难点不只是生成合法 SQL，而是同时解决：

- 用户说的业务词对应哪张表、哪个字段；
- “销售额”“活跃用户”“本月”等指标和时间表达具体代表什么；
- 多表查询应走哪条 JOIN 路径；
- SQL 虽然语法正确，结果是否符合用户意图；
- 查询失败时如何修复，如何避免模型无限重试；
- 私域数据如何保证不越权、不写库、可审计。

因此，系统的目标不是“让模型自由写 SQL”，而是给模型提供有限、可观察、可校验的执行空间。

### 1.2 三类请求

| 路由 | 作用 | 是否访问数据库 |
|---|---|---|
| `database_query` | 查询新的指标、明细、聚合、排名或对比数据 | 是 |
| `data_qa` | 解释、总结或分析已有结果表 | 否 |
| `direct_response` | 闲聊、能力询问或普通交流 | 否 |

这一步很重要：已有结果分析不应重新进入 Text-to-SQL；闲聊也不应触发 Schema 检索和数据库访问。V2 用一次结构化预处理调用同时完成路由、上下文改写和检索意图提取，见 `backend/app/preprocessing.py`。

### 1.3 一次数据库查询的全链路

```text
用户问题
  -> 认证与访问范围
  -> 请求预处理：路由、独立问题、检索意图
  -> 字段级 Schema 检索：BM25 + Dense + RRF + Rerank
  -> Schema 图构建：表、字段、关系和 JOIN 路径
  -> 单库 Agent：Skill 白名单 + 工具目录
  -> MCP：调用时间工具或数据库工具
  -> SQL AST 校验：只读、表、字段、权限
  -> DuckDB 执行 CSV
  -> 结果说明与结构化响应
  -> 会话、归档、记忆和执行日志
```

完整编排入口是 `backend/app/services/askdata_service.py`，工作流是 `backend/app/workflows/query_graph.py`，API 入口是 `backend/app/api/routes.py`。

### 1.4 为什么是 Agentic Workflow

固定节点和确定性校验组成 Workflow；在单库查询节点内部，模型根据当前观察结果选择工具、修复 SQL 或请求澄清，这部分具有 Agent 特征。因此更准确的称呼是 **Agentic Workflow**：

- 流程边界由工作流固定，便于审计和测试；
- 节点内部允许模型根据工具反馈动态决策；
- 每个模型输出都受到 JSON 契约、Skill、工具白名单和 SQL 校验约束。

它不是完全自由的通用 Agent，也不是不带动态决策的纯流水线。

## 2. Schema：Text-to-SQL 的知识边界

### 2.1 Schema 是什么

Schema 是数据库结构和业务语义的描述，至少包括：

- 表名、所属数据库和表的业务含义；
- 字段名、类型、注释、别名和业务角色；
- 主键、外键和业务关联关系；
- 枚举值、样例值、数据范围和统计特征；
- 指标口径，例如“月活跃用户”的具体定义。

没有 Schema，模型只能凭字段名和常识猜测，容易生成不存在的对象、错误的 JOIN 或口径错误的 SQL。Schema 同时是检索输入和 SQL 生成白名单。

### 2.2 三层 Schema 信息

| 层次 | 描述 | 在 V2 中的用途 |
|---|---|---|
| 表级 Schema | 表名、业务域、数据库、表关系 | 确定候选表和 JOIN 范围 |
| 字段级 Schema | 字段名、类型、语义、别名、角色 | 作为主要检索单元和 SQL 对象 |
| 数据级 Schema | 样例值、枚举、范围、分布和画像 | 辅助理解字段真实含义 |

V2 以字段作为索引单元，但字段文档会携带所属表和有限数据画像，因此一次字段召回可以同时覆盖表语义、字段语义和数据语义。直接对原始业务数据做大规模向量检索会增加成本和噪声，通常只保留代表性样例和统计特征。

### 2.3 为什么索引粒度选择字段

表级检索太粗：召回一张表并不能告诉模型应使用哪几个字段；数据级检索太细且数据变化频繁。字段是 SQL 生成的核心对象：查询列、筛选条件、聚合字段和 JOIN 键最终都要落到具体字段上。

字段又是表和数据的连接节点：向上可以取得表、数据库和关系，向下可以取得样例和画像。因此字段级索引在检索效果、上下文规模和维护成本之间取得了较好的平衡。

### 2.4 索引内容的分层

三路索引来自同一套 Schema 元数据，但不能简单复用同一段文本：

- 关键词索引强调字段名、别名、表名、业务术语和典型样例，保留离散精确信号；
- Embedding 索引强调精炼的核心业务语义，避免加入过多上下文造成向量稀释；
- Rerank 输入保留更丰富的字段、表、样例、统计特征和业务规则，用于精细区分相似字段。

如果字段描述发生变化，是否更新三类索引取决于变化影响的内容：新增别名通常更新关键词索引，语义变化需要更新 Embedding，业务规则或代表性画像变化需要更新 Rerank 文本。数据日常增长不必每次重建全部索引，但热点字段可以定期或按日志增量更新。

## 3. Schema 检索与图构建

### 3.1 混合检索流程

```text
standalone_query + retrieval_terms
  -> 权限过滤的候选字段
  -> BM25 关键词召回
  -> Dense 向量召回
  -> RRF 合并排名
  -> Rerank 精排
  -> 阈值过滤与字段数量限制
  -> SchemaGraphBuilder 构建最小连通图
```

V2 的实现位于 `backend/app/retrieval/service.py`、`store.py` 和 `graph.py`。

### 3.2 关键词、Dense 和 Rerank 各做什么

关键词检索适合字段名、编号、缩写和规范业务术语；对金融和企业数据尤其重要，因为词面命中往往比泛化语义更可靠。Dense 检索补充别名、口语化表达和用户描述与字段名不一致的情况。Rerank 使用原始 Query 与候选 Schema 的交互信息，对语义相近的字段做最后区分。

Rerank 不是第三种独立事实来源，而是对候选结果的精排阶段。混合召回追求高 Recall，Rerank 追求最终 Precision，不能在第一阶段就把候选截得过窄。

### 3.3 为什么用 RRF

BM25 分数和向量相似度通常不在同一量纲，直接相加需要复杂的归一化。RRF 只使用各路排名：

```text
RRF(d) = sum( weight_i / (k + rank_i(d)) )
```

它实现简单、对分数尺度不敏感，并允许一个结果只在某一路表现好时仍进入候选集合。V2 采用关键词主导、语义辅助的权重，这是业务选择而不是 RRF 的固有要求：当“成交额”漂移到“市值”会产生语法正确但口径错误的 SQL 时，应优先保护精确实体匹配。

### 3.4 Top-K 如何设置

Top-K 是召回率、噪声、上下文和延迟的折中：

- 太小会漏掉关键字段，下游无法凭空恢复；
- 太大会增加噪声、Token、Rerank 成本和模型选择难度。

工程上应先通过离线标注集测 Recall/Precision，再按 Query 复杂度、字段数量、业务风险和上下文预算动态调整。面经中的具体 Top-K、召回率和准确率数字属于 V1 口径，除非 V2 代码或报告有对应证据，不应写成 V2 指标。

### 3.5 最小连通 Schema 图

检索命中字段后，不能只把字段列表交给模型。`SchemaGraphBuilder` 会：

1. 收集命中字段所属的表；
2. 按关系元数据寻找多表之间的最短路径；
3. 补入必要的 JOIN 键字段；
4. 输出表、字段、JOIN 和 `graph_version`；
5. 同时生成结构化图和面向模型阅读的文本 Schema。

这样可以把“模型可以看到什么”和“模型可以怎么 JOIN”明确化。局部 Schema 是更小的后续子图；只有在查询计划或 Agent 真正需要时，才继续缩小上下文。

## 4. Agent、Workflow、Skill 与 MCP

### 4.1 Agent 的四种能力

面试中可以用“模型 + 工具 + 记忆 + 反馈循环”概括 Agent，但工程上要继续追问每个能力的边界：

- 模型负责理解和决策，不直接拥有数据库权限；
- 工具负责执行受控动作，并返回结构化结果；
- 记忆负责跨轮上下文和可复用经验；
- 反馈循环负责根据观察结果修复或终止。

V2 将这些能力放在工作流的不同节点中，而不是让一个模型同时承担所有职责。

### 4.2 V2 的工作流拓扑

```text
START
  -> preprocess
     -> respond_directly -> END
     -> answer_qa -> END
     -> retrieve_schema
        -> human_clarification -> retrieve_schema
        -> prepare_single_database
           -> human_clarification -> retrieve_schema
           -> execute_single_database -> END
        -> run_multi_database -> END
```

`database_query` 当前只支持单数据库直接查询；检索到多个数据库时返回明确的 Hand-off 未启用失败结果，而不是假装完成跨库查询。

### 4.3 Skill 解决什么问题

Tool 描述“能做什么”；Skill 描述“当前 Agent 被允许如何做”。V2 的 Skill 由配置和说明文件组成，包含名称、指令、允许工具、输出动作和调用预算。数据库查询 Skill 只能输出工具调用或澄清，data QA Skill 只能回答或生成报告。

Skill 的价值是把行为约束从 Prompt 中独立出来：

- 可按 Agent 角色收窄工具面；
- 可按需加载详细指令，减少常驻 Token；
- 可通过配置调整预算和动作，而不改主循环；
- 可以在代码层检查模型是否越过契约。

这就是渐进式披露：元数据常驻，详细指令按场景加载，脚本或参考资料只有真正需要时才使用。

### 4.4 MCP 解决什么问题

MCP 是工具访问协议，不等于模型本身的 Function Calling：

- Host 持有应用和模型上下文；
- Client 负责发现工具、发起调用和回传结果；
- Server 暴露工具并执行真实逻辑；
- 工具逻辑可以被不同 Client 复用。

典型时序是：

```text
用户问题
  -> Host 交给模型
  -> Client 向 Server 查询 tools/list
  -> 模型选择工具并生成参数
  -> Client 发起 tools/call
  -> Server 校验并执行
  -> Client 把结果交给模型
  -> Host 生成最终响应
```

V2 使用同进程 transport，但仍走完整 MCP 目录和调用协议。MCP 让工具边界标准化，Skill 决定当前 Agent 能看到和使用哪些工具。数据库护栏仍在工具实现内部，因此换协议不会绕过安全边界。

### 4.5 单库 Agent 的约束

单库 Agent 每轮获得独立问题、Schema 图、Schema 文本、用户确认信息、工具目录和已观察结果。它只能输出结构化 `call_tool` 或 `clarify`。调用目标数据库工具后立即返回结果，不允许在 SQL 已执行后自行继续访问其他数据库。

工具超限、非法动作和非法输出都会在工作流层形成显式失败。澄清使用 LangGraph 的 interrupt/resume：任务暂停，前端提交选项后恢复同一图状态，而不是把澄清回答当成一条全新的问题。

## 5. SQL 执行与安全边界

### 5.1 为什么 SQL 语法正确仍然不够

SQL 可以语法正确但业务错误，例如选错金额字段、使用错误时间字段、漏掉 JOIN 条件或访问越权表。因此执行前至少需要检查：语句结构、对象存在性、只读边界、访问范围、表关系和结果规模。

### 5.2 DuckDB CSV 执行器

V2 的演示数据库是 CSV 文件，DuckDB 每次创建内存连接，把目标数据库目录中的 CSV 注册为只读视图。这样可以模拟逻辑数据库，同时保持演示数据易分发、易重建。直接查询边界是单数据库，多库路径当前明确失败。

### 5.3 执行前 AST 校验

`backend/app/querying/duckdb_engine.py` 使用 sqlglot 对 SQL 做白盒检查：

1. 去掉代码块和末尾分号后，只接受一条语句；
2. 根节点必须是 `SELECT` 或 `WITH` 查询；
3. 拒绝写操作、DDL、复制、外部挂载、事务和授权语句；
4. 拒绝 `*` 和 `<table>.*`，避免无意暴露整表数据；
5. 检查目标数据库权限；
6. 从 AST 提取真实表引用，排除 CTE 名称；
7. 每张表都必须属于当前数据库并通过用户白名单校验。

执行最多读取 201 行，响应最多返回前 200 行，并把日期、Decimal 等值转换成可 JSON 序列化的类型。

### 5.4 失败处理原则

安全拒绝、权限失败和 SQL 执行异常都必须形成显式失败结果，不能用模板伪造数据答案。可修复的 SQL 错误可以回传给 Agent；不可重试的越权和写操作应直接终止。成功执行后，如果结果说明模型失败，仍然保留 SQL、列和行，只把说明标记为失败。

## 6. 会话、记忆与工作区

### 6.1 四种上下文必须分开

| 上下文 | 用途 |
|---|---|
| `route_context` | 最近几轮的轻量信息，用于判断新问题还是追问 |
| `short_term_context` | 滑动窗口和异步摘要，用于已有结果问答 |
| `recent_result_context` | 最近一次成功查询的有限结果 |
| `analysis_context` | 用户明确拖入的历史结果表 |

Schema 字段工作区只服务新查询；历史结果工作区只服务 `data_qa`。如果不分开，用户拖入的旧结果可能污染新一轮 Schema 检索。

### 6.2 短期记忆

会话保存用户和助手回合，超过 Token 阈值后异步把较早的完整回合合并为摘要，同时保留最近若干轮原文。路由只读取轻量近期记录，不读取可能改变意图判断的长摘要。

### 6.3 长期记忆

V2 的长期记忆包括成功结果表和用户收藏字段。结果表以任务 ID、问题、标题、列和有限行保存，data QA 只能引用显式存在于 `source_catalog` 的结果。字段或结果收藏按用户隔离并有数量上限。

与 V1 自动沉淀样例不同，V2 对可复用 QA 采用候选池与正式库：双通过结果先进入候选池，用户确认后才进入检索范围。这样减少错误 SQL 自动污染长期记忆。

### 6.4 结果不是永久快照

大结果集不能无条件塞进上下文。小结果可以保留有限原文，大结果应保留问题、SQL、列、行数、统计特征和代表性样本。真正需要再次分析时，应优先引用任务结果或重新执行可重放的查询，而不是把无限数据复制到 Prompt。

## 7. 结构化结果与前端体验

### 7.1 ResultBuilder 的职责

`ResultBuilder` 是 API 结果的统一装配层，为三类路由设置一致的 `QueryResult`，并汇总：

- 状态、路由和路由原因；
- SQL、列、行和结果来源；
- Schema 检索和图信息；
- MCP 调用轨迹和执行日志；
- 澄清问题、报告和图表规格。

统一装配层可以避免不同失败路径返回完全不同的响应结构，也方便前端、测试和故障定位复用。

### 7.2 已有结果问答

`data_qa` 不访问数据库，只接收用户明确选择的已有结果。Agent 先建立 `source_catalog`，只允许引用其中的任务、列和行，再选择回答或报告动作。图表工具调用前，后端还要验证来源任务和字段确实存在，防止模型凭空引用会话外数据。

### 7.3 前端工作区

前端负责登录、会话、Schema 字段拖入、历史结果拖入、澄清恢复、结果表、SQL、检索过程、报告和图表展示。前端可以保存本地历史，但后端仍接收必要的工作区载荷，以支持后端任务内存重启后的继续使用。

## 8. 错误、观测与可维护性

### 8.1 分阶段失败

| 阶段 | 处理 |
|---|---|
| 预处理模型不可用 | 保守返回直接回复，不进入数据库路径 |
| Schema Embedding/Rerank 失败 | 返回带阶段信息的显式失败 |
| Skill 输出非法或工具超限 | 标记 Agent 阶段失败 |
| SQL 不合法、越权或执行异常 | 返回失败 SQL、错误、Schema 和日志 |
| SQL 成功但结果说明失败 | 保留成功数据，说明明确失败 |
| 多库检索 | 返回当前未实现的 Handoff 失败 |

### 8.2 需要记录什么

每个任务至少应记录：用户、会话、原问题、路由、路由原因、检索结果、Schema 图版本、每步工具、工具参数、执行耗时、Token、SQL、返回行数、终止原因和错误信息。

可观测性不是“打印更多日志”，而是让每一个决定都能回答：谁做的、依据什么、访问了什么、结果是什么、失败在哪里。

## 9. 测试与评测

### 9.1 行为测试优先

模型输出具有不确定性，测试不应依赖真实模型每次给出同样文本，而要用 FakeModelClient 固定关键决策，验证系统边界：

- 三类路由和模型不可用退化；
- Schema 检索、RRF、图构建和权限过滤；
- MCP 工具目录、参数契约和工具隐藏；
- SELECT-only、通配符、写 SQL、CTE 越权和结果序列化；
- 澄清 interrupt/resume、单库查询、JOIN 和 data QA；
- 短期摘要、会话归档、长期记忆用户隔离；
- 失败结果、日志和前端响应契约。

### 9.2 Text-to-SQL 的正确性评测

不能只比较 SQL 字符串。等价 SQL 可能有不同写法，应执行 Agent SQL 和金标 SQL，并比较结果集，同时辅以：

- 语法有效率；
- 表和字段召回 Recall/Precision；
- 平均步数、Token、延迟和工具调用次数；
- SQL 错误修复成功率；
- 澄清触发率；
- 记忆开关的消融差异。

记忆没有带来提升时也要如实报告，检查样例数量、检索质量、注入位置和数据分布，而不是为了得到好看的指标修改判定规则。

## 10. V1 → V2 演进对照

| 主题 | V1 面经口径 | V2 当前口径 |
|---|---|---|
| Agent 结构 | CoT、Coder、Reflection 三 Agent | LangGraph 工作流 + Skill 约束的单库 Agent + data QA Agent |
| 规划表示 | 四元组 CoT | 预处理结构化意图 + Schema 图 + Agent 工具决策 |
| 检索 | 三级索引的概念描述 | 字段级文档、BM25/Dense/RRF/Rerank 的代码实现 |
| 向量库 | Chroma 或 Milvus 的项目叙事 | 本地 JSON Schema store，Milvus 是可选企业形态；以当前代码为准 |
| 数据执行 | MCP 路由到多个数据库 | DuckDB CSV，单库查询；多库明确失败 |
| 记忆 | 自动沉淀长短期记忆 | 短期摘要 + 用户隔离的结果/字段记忆 + QA 候选确认 |
| 澄清 | 模型回调用户通道 | LangGraph interrupt/resume，任务状态可恢复 |
| 输出 | SQL 和查询结果 | 统一 QueryResult、结果说明、报告、图表规格和完整轨迹 |

V2 的改良方向不是单纯增加组件，而是把模型可自由发挥的地方收窄，把权限、状态、输出和失败处理变成代码契约。

## 11. 面试问题学习索引

### 项目定位

回答“为谁做、解决什么问题、是否上线”时，应先说明私域数据库、业务人员不会 SQL、数据不能出域，再说明受控问数链路和当前部署边界。不要先堆技术名词。

### Agent 与 Workflow

回答“是 Agent 还是 Workflow”时，使用 Agentic Workflow：工作流负责固定阶段和安全边界，Agent 在单库执行节点内根据观察结果动态选择工具、修复 SQL 或请求澄清。

### Schema 与检索

回答“为什么字段级、为什么混合检索、为什么 RRF、Rerank 做什么”时，依次说明：字段是 SQL 核心对象；关键词保护精确实体，Dense 补充语义泛化；RRF 解决分数不可直接比较；Rerank 负责候选字段的细粒度区分。

### Tool Calling、MCP 与 Skills

回答“Function Calling、MCP、Skill 的关系”时，区分三个层次：模型输出调用意图，MCP 标准化工具发现和执行协议，Skill 约束 Agent 在具体场景可使用的工具与动作。MCP 不是安全授权本身，真正权限和 SQL 护栏仍在服务端代码。

### SQL 安全与结果正确性

回答“如何保证安全和准确”时，不要只说 Prompt：列出 AST 单语句/SELECT-only、表字段存在性、用户访问范围、禁止通配符、结果行数限制、序列化、失败回传和日志审计。再说明语法正确不等于业务正确，需要 Schema 语义、JOIN 图和结果集评测共同保证。

### 版本辨析

如果面试官追问 V1 的 CoT、Reflection、Chroma 或旧指标，应主动说明它们是历史方案或面试知识，V2 已做了结构收敛，并指出当前代码中的对应实现。能清楚讲出“保留了什么、替换了什么、为什么替换”，比把两个版本混成一个更可信。

## 13. 当前边界与不要过度声称的内容

- 当前直接查询边界是单数据库；多库 Handoff 尚未启用；
- 当前认证是本地 Mock，不等于生产身份系统；
- 当前长期记忆是本地 JSON/可选归档形态，不等于完整企业级记忆平台；
- 当前测试主要证明行为契约，不代表真实模型在所有业务口径上都正确；
- 任何召回率、准确率、延迟、并发量和上线规模，都必须绑定版本、数据集和实验记录；
- 面经中的通用 RAG 图、MCP 图和 Agent 图用于理解概念，不能自动证明 AskData 代码实现了图中所有能力。

学习这类项目的最终目标，不是记住一条“标准 Agent 架构”，而是能从业务风险出发解释每个边界：哪些交给模型，哪些由代码决定，哪些必须允许失败，以及如何用数据和测试验证设计是否真的有效。
